Audio and Video Calls Guide

« Back to documentation index

Introduction

Which configuration works best depends heavily on the networks that your users and your server are in. This guide is not exhaustive, but aims to describe common setups.

Many XMPP clients can make audio and video calls. This guide describes what is needed, on the side of Openfire and the network that it is in, to allow such calls to connect reliably.

How calls are connected

A one-to-one call between two XMPP clients is set up using Jingle. Openfire is used to deliver the messages with which the clients negotiate the call, but the audio and video itself does not pass through Openfire. Instead, the clients try to send it directly to each other.

Clients find a way to reach each other using ICE (Interactive Connectivity Establishment). Each client gathers a list of addresses on which it can possibly be reached (its candidates), sends that list to the other client, after which both try every combination until one works. Clients use three kinds of candidates:

Host candidates
The addresses of the network interfaces of the device itself. These work when both clients are in the same network, or when a client has a public IP address.
Server-reflexive candidates
The public address that a NAT router uses for the client. A client learns this address by asking a STUN server. These often work when one or both clients are behind a home router.
Relayed candidates
An address on a TURN server, which relays all audio and video between the clients. This works in nearly all cases, including networks where direct connections are impossible, such as many mobile networks (which commonly use carrier-grade NAT) and corporate networks.

Without a STUN or TURN server, calls typically only connect when both clients are in the same network. With STUN, many (but not all) calls over the internet connect. A TURN server is needed to make calls connect reliably. As a TURN server relays the audio and video of calls that cannot be connected directly, it needs enough bandwidth for those calls.

Clients learn which STUN and TURN servers to use by asking their XMPP server, using XEP-0215: External Service Discovery. Openfire does not provide that functionality itself: it is added by a plugin, as described below.

Components

A typical setup consists of a STUN/TURN server, and the External Service Discovery plugin that tells clients how to use it. All plugins mentioned in this guide can be installed from the Plugins page of the Openfire Admin Console, or downloaded from the Openfire plugins page.

External Service Discovery plugin

The External Service Discovery plugin implements XEP-0215. After installation, it can be configured on the Server > Media Services > Ext. Service Discovery page of the Admin Console. Add an entry for each STUN or TURN service that clients should use. Each entry consists of a host, a port, a transport (UDP or TCP), a type (STUN, TURN or TURNS) and, for TURN, the credentials that clients need to use the service (see Credentials for TURN).

This plugin is needed regardless of which STUN/TURN server is used, as without it, clients will not learn about the server.

Pion TURN plugin

The Pion TURN plugin runs a STUN/TURN server (based on the Pion TURN project) on the same machine as Openfire. It is the easiest way to add a TURN server to an Openfire installation, as no additional software needs to be installed or managed. The plugin reads its configuration from the External Service Discovery plugin, which needs to be installed too. The README of the plugin describes how to configure both plugins.

Be aware of the following limitations:

  • It contains executables for 64-bit Linux and 64-bit Windows only.
  • It uses UDP only. It does not provide TURN over TCP or TLS, which some clients need in networks that block UDP traffic.
  • It relays traffic on the IP address that is configured in the plugin. That needs to be an address that is reachable by all clients, which in practice means a public IP address. When Openfire runs behind a NAT router, the public IP address of the router needs to be configured, and the router needs to forward the TURN port (default: 3478) and the entire relay port range (default: 50000-55000) to Openfire, for UDP.
  • A firewall on the server needs to allow UDP traffic on the same ports.

A standalone STUN/TURN server

Instead of using the Pion TURN plugin, you can install a dedicated STUN/TURN server, such as coturn or eturnal. These can run on the same machine as Openfire, or on a different machine. Compared to the Pion TURN plugin, these servers offer more options, including TURN over TCP and TLS, and explicit configuration for running behind NAT. Configuring and maintaining them is not covered by this guide: please refer to their documentation.

Once the server is running, add its services to the External Service Discovery plugin. When possible, configure the TURN server to use a shared secret (see Credentials for TURN). For coturn, this is done with these options in its configuration file: 

use-auth-secret
static-auth-secret=a long, random, alphanumeric secret
realm=example.org

A server that is used by clients on various networks typically gets four entries in the External Service Discovery plugin: STUN over UDP, TURN over UDP and TURN over TCP (all commonly on port 3478), and TURNS (TURN over TLS, commonly on port 5349 or 443) to support clients in networks that only allow encrypted web traffic.

Credentials for TURN

A TURN server relays traffic for anyone that can authenticate with it. Without proper access control, others can use your server, and your bandwidth. The External Service Discovery plugin can give clients credentials in two ways:

Shared secret (recommended)
The plugin and the TURN server share a secret. For every client that asks, the plugin uses that secret to generate a username and password that are valid for 24 hours. This is the mechanism that is commonly known as the "TURN REST API", which is supported by coturn, eturnal and the Pion TURN plugin. The secret itself is never given to clients.
Static username and password
All clients get the same username and password. Anyone that has ever obtained these can keep using the TURN server, until the password is changed on both the server and in the plugin.

Use a long secret or password that consists of letters and digits only. Special characters have been reported to cause problems.

Common environments

All users are in the same network

When all users are in the same local network (for example, an office network in which Openfire is used internally), clients can usually reach each other using host candidates. No additional configuration is needed. When there are several network segments that are separated by a firewall, the firewall needs to allow UDP traffic between those segments, or a TURN server needs to be added.

Openfire runs on a server with a public IP address

This is the case for many servers that are hosted in a data center or with a cloud provider. Here, the simplest setup is to install the Pion TURN and External Service Discovery plugins. Make sure that the firewall of the server (and of the hosting provider, if any) allows UDP traffic on the TURN port and the relay port range.

When users are expected to be in restrictive networks, such as corporate networks that block UDP traffic, use a standalone TURN server that also offers TURN over TCP and TURNS.

Openfire runs behind a NAT router

This is common when Openfire is installed in a home or office network, and users connect to it from the internet. A TURN server needs to be reachable from the internet. There are two options:

  • Run the TURN server in the same network as Openfire (either using the Pion TURN plugin, or a standalone TURN server). Configure it with the public IP address of the router, and configure the router to forward the TURN port and the entire relay port range to the TURN server. If the public IP address changes from time to time, the configuration needs to be updated whenever that happens.
  • Run a standalone TURN server elsewhere, on a machine that has a public IP address (for example, a small virtual server that is hosted with a cloud provider), and add it to the External Service Discovery plugin. This avoids the need to forward a large range of ports.

Openfire runs in a container

When Openfire runs in a container (for example, using Docker), the container usually has an internal IP address that is translated to the address of the host, much like a NAT router does. The considerations for running behind a NAT router apply.

Mapping a large range of UDP ports into a container is often slow or impractical. When running a TURN server (or the Pion TURN plugin) in a container, consider using the network of the host directly (with Docker, by using --network host), or run the TURN server outside of the container.

When the host has a public IPv6 address but a translated IPv4 address, clients that have IPv6 connectivity may be able to reach each other directly, but clients that only have IPv4 connectivity still need a TURN server that is reachable over IPv4.

Group calls

The setup described above is for calls between two people. Calls with more participants are commonly handled by a server component that receives the audio and video of every participant and forwards it to all others (a Selective Forwarding Unit, or SFU). Several plugins provide such functionality, including Galene and Openfire Meetings (based on Jitsi Meet). These have their own network requirements, which are described in their documentation.

Legacy options

Some plugins provide functionality that predates the mechanisms described in this guide. Current clients are not known to use these.

STUN server plugin
Runs a STUN server (but not a TURN server), which is configured with two IP addresses. Clients learn about it through the google:jingleinfo protocol of Google Talk, rather than through External Service Discovery.
Jingle Nodes plugin
Relays traffic for clients that implement XEP-0278: Jingle Relay Nodes.
RTP Bridge plugin
Relays traffic for clients that use a protocol that was never standardized. This was part of Openfire until version 5.2.0, where it was known as the Media Proxy. It was used by the voice call functionality of older versions of Spark.

Troubleshooting

  • When calls connect in the same network but not over the internet (for example, when one of the users switches from Wi-Fi to a mobile network), a TURN server is missing, unreachable, or not announced to clients.
  • When calls connect but no audio or video arrives, the relay port range of the TURN server is often not reachable. Check the firewall and port forwarding configuration.
  • When using the Pion TURN plugin, restart the plugin (from the Plugins page of the Admin Console) after changing its configuration.
  • Some clients show which services are announced by the server. Conversations, for example, lists these in its server information screen.
