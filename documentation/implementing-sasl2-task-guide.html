Custom SASL2 Task Guide

« Back to documentation index

Introduction

This document explains how to extend Openfire's authentication process with a SASL2 task: a step that runs after a client has proven its identity, but before it is granted access. Tasks are how Openfire supports things like a second authentication factor, a mandatory acceptance of updated terms of service, or a one-time upgrade of stored credentials, without any of that logic living in the SASL mechanism itself.

The API is small, but the protocol it drives (defined in XEP-0388: Extensible SASL Profile) has a few moving parts, so this guide spends some time on the flow before it gets to the code.

Background

SASL2 (the SASL profile defined by XEP-0388) authenticates a client in a single round trip in the common case: the client sends an <authenticate/> element, the server verifies it, and a <success/> comes back. XEP-0388 defines an optional extension to that flow: after the SASL exchange itself has succeeded, but before <success/> is sent, the server may require the client to complete one or more tasks. Each task is a small, self-contained exchange of its own, using <task-data/> elements whose content is entirely up to the task.

A task is not a SASL mechanism. It does not verify a password or a certificate; the SASL exchange has already done that by the time a task runs. A task is better understood as a gate that sits between "the client proved who it claims to be" and "the client now has a logged-in session".

This makes the task flow a good fit for requirements that are orthogonal to identity verification, such as:

  • a second authentication factor (a TOTP code, a WebAuthn challenge, a push approval);
  • enforcing acceptance of updated terms of service before a session is allowed to proceed;
  • having a client that authenticated with a password derive and hand over credentials for a stronger mechanism, so it can use that mechanism next time (this is the pattern described by XEP-0480: SASL Upgrade Tasks);
  • anything else that should run once, exactly at login time.

The API described in this guide, org.jivesoftware.openfire.sasl.task, is a registry that third-party code plugs into.

The task negotiation, on the wire

It helps to have seen the shape of the protocol before looking at the Java API that drives it. The example below is a task that asks the client to accept a piece of text (the pattern used by the terms of service example discussed later in this guide):

A SASL2 negotiation that includes one task 
C: <authenticate xmlns='urn:xmpp:sasl:2' mechanism='SCRAM-SHA-256'>
     <initial-response>...</initial-response>
   </authenticate>
...
S: <continue xmlns='urn:xmpp:sasl:2'>
     <tasks><task>TOS-ACCEPT</task></tasks>
     <text>The terms of service have changed and must be accepted before you can sign in.</text>
   </continue>
C: <next xmlns='urn:xmpp:sasl:2' task='TOS-ACCEPT'/>
S: <task-data xmlns='urn:xmpp:sasl:2'>
     <terms xmlns='urn:xmpp:termsofservice:0' version='2026-01'>https://example.org/tos/terms</terms>
   </task-data>
C: <task-data xmlns='urn:xmpp:sasl:2'>
     <accept xmlns='urn:xmpp:termsofservice:0' version='2026-01'/>
   </task-data>
S: <success xmlns='urn:xmpp:sasl:2'>...</success>

A few things worth noting about this flow, since they shape the API:

  • The SASL exchange itself (the <authenticate/> / challenge-response part) has already finished by the time <continue/> is sent. Any success data the mechanism produced travels in that first <continue/>, not in a separate <success/>: the session is not yet authenticated, so nothing that marks it as such (a resource binding, a FAST token, an inline stream resumption) has happened yet.
  • <tasks/> can list more than one task name. That is a set of alternatives, not a sequence: the client picks exactly one with <next task='...'/>. To require several tasks one after another, the server sends a further <continue/> once the first has completed.
  • Everything inside <task-data/> is opaque to the framework. Its meaning is defined entirely by the task; the child elements carry their own namespace.
  • A client that does not understand a task it is offered can only abort. There is no "decline"; see Deciding when to offer a task for how to avoid locking out clients that were never written with a particular task in mind.

The extension points

Four types make up the API, all in org.jivesoftware.openfire.sasl.task. Openfire's SASLAuthentication class drives them; a task author never calls into SASLAuthentication directly.

Sasl2TaskProvider

The Sasl2TaskProvider interface is what you implement and register. One instance serves every session concurrently, so it must be thread-safe; it holds no per-negotiation state itself. Its methods are invoked, per negotiation, in this order:

getStreamFeatureElements(LocalSession)
optional. Lets a task advertise itself in the SASL2 <authentication/> stream feature, before the client has even authenticated, so that it can discover and opt in to the task. Defaults to advertising nothing.
onAuthenticateReceived(Sasl2TaskContext, Element)
optional. Called with the client's <authenticate/> element, before the SASL exchange has completed. This is where an opt-in the client inlined into that element is parsed and stashed as a context attribute for later. Defaults to doing nothing.
getOfferedTasks(Sasl2TaskContext)
required. The eligibility check: given everything known about this negotiation so far, which of this provider's tasks (if any) should be offered right now? Called once the SASL exchange has succeeded, and again after every task completes, so that a provider can offer a further task or withdraw an alternative that another provider's task already satisfied.
createTask(String, Sasl2TaskContext)
required. Called once, when the client selects one of the task names this provider offered, to produce the Sasl2Task instance that will run it.
getContinueText(Sasl2TaskContext)
optional. Human-readable text to include in the <continue/> element, when this provider contributed a task to that round.
onNegotiationEnded(Sasl2TaskContext, boolean)
optional. Called exactly once per negotiation this provider participated in, successful or not, so it can release anything it allocated. See the note on the successful parameter in the Javadoc: it reports the outcome of the task flow, not of the SASL2 negotiation as a whole.

A provider also declares a stable getIdentifier() and the full set of getTaskNames() it can ever offer. Both are checked for collisions with other registered providers at registration time. An optional getPriority() (default zero) controls the order in which providers are consulted; higher values run first, which matters when a client is offered tasks from more than one provider in the same round.

Sasl2Task

Sasl2Task is the stateful, per-negotiation counterpart to the provider: a fresh instance is created for every negotiation in which the client selects it, and it is never reused across sessions. Its contract is small:

  • begin(Element next) is invoked with the client's <next/> element (which may itself carry a payload, letting a simple task finish in one round trip).
  • Whenever a step returns Sasl2TaskResult.taskData(...), Openfire sends a <task-data/> element and the client's reply is delivered to onTaskData(Element). This repeats for as long as the task needs; the default implementation of onTaskData(...) aborts the negotiation, which is correct for a task that never expects data back.
  • Returning Sasl2TaskResult.completed() (optionally carrying <additional-data/>) finishes the task.
  • Throwing SaslFailureException at any point aborts the entire SASL2 negotiation, not just the task: the client gets <failure/>, and no resource is bound and no inline stream resumption can take place, even though the password (or other mechanism) had already checked out.
  • onAborted() is called if the negotiation ends while the task is still in progress (the client aborted, another task failed, the connection dropped). It must not write to the session, and must be safe to call on a task that never started or has already finished cleaning up.

Sasl2TaskContext

Sasl2TaskContext is the window a provider (and the tasks it creates) has onto one negotiation. Each provider gets its own view: getAttribute(...) / setAttribute(...) scratch storage is scoped per provider identifier, so two providers using the same attribute name never collide. Besides attribute storage, the context exposes:

isAuthenticated() / getAuthorizationIdentity()
only meaningful once the SASL exchange has succeeded; both are unset (false / null) during onAuthenticateReceived(...).
getSaslMechanismName()
the mechanism the client used. Before authentication has succeeded this is only the client's claim, not yet verified; do not base an eligibility decision on it until isAuthenticated() is true.
getChannelBindingType(), getUserAgentInfo()
useful for making a task conditional on how the client connected, or on which client it is (see below). User agent information is client-supplied and should not be trusted.
getCompletedTaskNames(), getOfferedTaskNames(), getRound()
the negotiation's history so far, useful for a provider offering a choice of alternatives.
getAdvertisedFeatureElements()
the elements this provider itself put into the stream feature earlier, so it can validate a client's request against what it actually offered rather than trusting the request outright.

Sasl2TaskResult

Sasl2TaskResult is the small, immutable value a Sasl2Task step returns: either Sasl2TaskResult.taskData(Element...) or Sasl2TaskResult.completed() / Sasl2TaskResult.completed(byte[] additionalData). There is no way to signal a soft failure through this type. A step that must reject the client's input throws SaslFailureException instead.

Sasl2TaskManager

Sasl2TaskManager is the singleton registry (Sasl2TaskManager.getInstance()) and the driver of the flow described above. As a task author you mostly interact with it only to register and unregister your provider; see the next section.

Registering a provider

Unlike the AuthProvider extension point, a Sasl2TaskProvider is designed to be registered and unregistered at runtime, and this is the recommended way to deploy one: from an Openfire plugin's initializePlugin(...) and destroyPlugin().

Registering from a plugin 
public class MyPlugin implements Plugin {

    private Sasl2TaskProvider provider;

    @Override
    public void initializePlugin(PluginManager manager, File pluginDirectory) {
        provider = new MyTaskProvider();
        Sasl2TaskManager.getInstance().register(provider);
    }

    @Override
    public void destroyPlugin() {
        Sasl2TaskManager.getInstance().unregister(provider);
    }
}

Unregistering does not disturb a negotiation that is already in progress: a running negotiation holds a direct reference to the provider and to the Sasl2Task instances it created, so an in-flight client is unaffected by a plugin reload that happens mid-negotiation. See the FAQ for why this is a better fit for a plugin than the lib-directory approach used by AuthProvider and similar interfaces.

register(...) throws IllegalArgumentException if the identifier is empty, if no task names are declared, or if either the identifier or one of the task names is already claimed by another registered provider. Check for this at plugin start-up; a collision usually means two plugins (or two versions of the same plugin) are both active.

Deciding when to offer a task

getOfferedTasks(Sasl2TaskContext) is where the real design decisions live. Because a client faced with an unrecognised task can only abort the entire login, offering a task unconditionally locks out every client that has not implemented it. There are three patterns for avoiding that, and which one applies depends on whether the task is optional or mandatory:

  • Opt-in (recommended for optional tasks). Advertise the task via getStreamFeatureElements(...), and only return it from getOfferedTasks(...) if onAuthenticateReceived(...) recorded that the client actually asked for it. This is the pattern used for a credential upgrade: a client that never requests the upgrade is never offered it.
  • Client-conditional. Use Sasl2TaskContext.getUserAgentInfo() to restrict the offer to client software that is known to support the task. Since user agent data is client-supplied, treat this as a courtesy to well-behaved clients rather than a security boundary.
  • Unconditional / mandatory. Appropriate for a task that genuinely must be performed by the users it applies to, like a second factor required on an account, or acceptance of terms of service that changed. There is no opt-in to check; the eligibility logic instead checks server-side state (has this account already completed this, does this apply to this account at all) and offers the task to everyone the check applies to, including clients that have never seen it before. Those clients will simply be unable to log in until they add support for the task, so use this pattern deliberately. Note that this only holds for clients authenticating via SASL2; see Security and threading notes for what "mandatory" actually means if this server also accepts the legacy SASL profile.

Openfire isolates providers from each other: if getOfferedTasks(...) throws, the exception is logged and that provider is skipped for the round rather than failing the whole negotiation. This fail-open behaviour is convenient for optional tasks, but it means a mandatory task must fail closed from within its own eligibility check (for example, by treating "I could not determine whether this task is needed" as "yes, offer it") rather than relying on the manager to do that for it.

A related point: getStreamFeatureElements(...) runs for every session that reaches feature advertisement, including ones that have not authenticated yet. Anything this method does is reachable by an unauthenticated peer, and anything it varies on is observable by one. Keep this method cheap and, ideally, independent of any claimed identity.

Configuration

The task flow as a whole is governed by three dynamic system properties, independent of any individual provider's own configuration:

xmpp.auth.sasl2.tasks.enabled
Boolean, default true. The overall kill switch: when set to false, no task is advertised or offered by any provider, and a client that sends <next/> or <task-data/> anyway has its negotiation failed. Useful if a third-party provider misbehaves in production and needs to be taken out of the loop without a restart.
xmpp.auth.sasl2.tasks.disabled
A comma-separated list of provider identifiers (see getIdentifier()). Lets an administrator disable one specific provider while leaving every other registered provider, and the plugin that supplies the disabled one, running.
xmpp.auth.sasl2.tasks.max-rounds
Integer, default 5. The maximum number of <continue/> elements sent during a single negotiation. This bounds the damage a provider can do if it keeps offering a task that never becomes ineligible; exceeding it fails the negotiation rather than looping forever. It is not usually something a task author needs to think about, beyond making sure getOfferedTasks(...) reliably stops returning a task's name once that task has actually been completed.

Security and threading notes

Task enforcement is scoped to SASL2. A client is only ever offered a task if it authenticates using the SASL2 profile defined by XEP-0388; the <continue/> / <next/> / <task-data/> exchange has no equivalent in the legacy SASL profile of RFC 6120. If this server is configured to also accept that legacy profile, or any other authentication path that does not go through SASL2, a client that authenticates over one of those paths never sees a task at all, and none of the requirements a task implements (a second factor, a mandatory terms-of-service acceptance, a credential upgrade) are enforced on it. A task is therefore only as mandatory as the set of authentication paths this server is configured to accept; if legacy SASL should not be an escape hatch around a task, that has to be addressed in your mechanism/connection configuration, not in the task itself.

A task runs after the SASL exchange has already succeeded. Openfire holds back everything that would mark the session as authenticated &mdash (the authentication token, resource binding, FAST token issuance, inline XEP-0198 stream resumption, etc.) until every eligible task has completed, so a task can genuinely function as an additional factor.

There is a limit to that, worth keeping in mind when designing a task: it cannot protect against an attacker who already holds valid credentials and is willing to simply abandon the connection. The password (or other mechanism) was verified before the task ran, so a failed task confirms to that attacker that the credential was correct, even though no session was ever granted.

On threading: a provider instance is shared across every concurrent session, so it must be thread-safe. Sasl2Task and Sasl2TaskContext instances are scoped to one negotiation and are never invoked concurrently for that negotiation, but they are not synchronized for you either. Avoid holding a reference to one beyond the negotiation it belongs to. Task methods are called on the thread that processes inbound data for the client's connection and must not block: a quick database round trip is fine, a call-out to a third-party service is not, since there is currently no support for resolving a task step asynchronously.

Walkthrough: writing a task

The steps below build a minimal, mandatory, single-round-trip task: one that simply asks the client to echo back a value the server sends it. It deliberately skips the opt-in machinery (getStreamFeatureElements(...) / onAuthenticateReceived(...)); add that if your own task is optional, per Deciding when to offer a task.

  1. Pick a stable provider identifier and a task name, and declare them:

    Provider skeleton 
    public class MyTaskProvider implements Sasl2TaskProvider {

    static final String TASK_NAME = "MY-TASK";

    @Override
    public String getIdentifier() {
        return "org.example.my-task";
    }

    @Override
    public Set<String> getTaskNames() {
        return Set.of(TASK_NAME);
    }
    // ...
}

  2. Implement the eligibility check. This example is mandatory for every non-anonymous login that has not completed it yet in this negotiation:

    getOfferedTasks(...) 
    @Override
public List<String> getOfferedTasks(Sasl2TaskContext context) {
    if (context.getAuthorizationIdentity() == null) {
        return List.of(); // nothing to gate for an anonymous login
    }
    if (context.getCompletedTaskNames().contains(TASK_NAME)) {
        return List.of();
    }
    return List.of(TASK_NAME);
}

  3. Produce a task instance when the client selects it:

    createTask(...) 
    @Override
public Sasl2Task createTask(String taskName, Sasl2TaskContext context) {
    return new MyTask();
}

  4. Implement the task itself. Here, one round trip is enough:

    The task 
    private static class MyTask implements Sasl2Task {

    private static final String NAMESPACE = "urn:example:my-task:0";

    @Override
    public String getName() {
        return TASK_NAME;
    }

    @Override
    public Sasl2TaskResult begin(Element next) {
        Element challenge = DocumentHelper.createElement(QName.get("challenge", NAMESPACE));
        challenge.setText("some-value");
        return Sasl2TaskResult.taskData(challenge);
    }

    @Override
    public Sasl2TaskResult onTaskData(Element taskData) throws SaslFailureException {
        Element response = taskData.element(QName.get("response", NAMESPACE));
        if (response == null || !"some-value".equals(response.getTextTrim())) {
            throw new SaslFailureException(Failure.NOT_AUTHORIZED, "Unexpected response.");
        }
        return Sasl2TaskResult.completed();
    }
}
  5. Register the provider from your plugin's initializePlugin(...), as shown in Registering a provider, and unregister it from destroyPlugin().
  6. Restart (or reload) the plugin. On the next SASL2 login, the client should receive a <continue/> offering MY-TASK, and cannot complete authentication until it responds correctly.

Two more complete, worked examples exist, illustrating each of the offering patterns described earlier:

  • A terms-of-service acceptance task (mandatory pattern): it offers TOS-ACCEPT to every account whose recorded acceptance is not for the currently active document version, walks the client through a <terms/> / <accept/> exchange, and records the acceptance once the version presented in begin(...) matches the version accepted in onTaskData(...) (guarding against the document being changed mid-negotiation). This task is part of the "Terms of Service" plugin for Openfire.
  • A SCRAM credential upgrade task (opt-in pattern), modelled on XEP-0480: it advertises the mechanisms it can upgrade to only over an encrypted connection, records a client's opt-in from its <authenticate/> element after validating it against what was actually advertised, and only then offers the corresponding UPGR-<mechanism> task.

Both use only the public API described in this guide, and are a good reference for questions this guide does not answer directly.

Frequently Asked Questions

Do I have to implement every method on Sasl2TaskProvider?

No. Only getIdentifier(), getTaskNames(), getOfferedTasks(...) and createTask(...) are required. getStreamFeatureElements(...), onAuthenticateReceived(...), getContinueText(...), onNegotiationEnded(...) and getPriority() all have sensible defaults for a task that does not need them.

Can I offer more than one task from a single provider?

Yes. getTaskNames() and the list returned by getOfferedTasks(...) are not limited to one entry. This is the mechanism used to offer several second-factor alternatives at once (the client picks one), or to require unrelated tasks from the same provider in sequence (return the next one only after the previous has completed).

Can I have more than one Sasl2TaskProvider registered at the same time?

Yes, and this is the normal case: separate concerns (a terms-of-service check, a second factor, a credential upgrade) are expected to live in separate providers, possibly shipped by separate plugins. They are consulted independently every round, in descending order of getPriority(). The only constraint is that no two registered providers may declare the same identifier or the same task name.

Isn't it better to deploy this as a jar on the classpath, like an AuthProvider?

For Sasl2TaskProvider, no. This is the opposite recommendation from the Custom Authentication Provider Guide, and deliberately so. AuthProvider and similar interfaces are read from a static configuration property at start-up, so Openfire needs them to be reliably present on the classpath for the service's entire lifetime. Sasl2TaskManager, by contrast, is a runtime registry built around register(...) / unregister(...) calls, specifically so that a plugin can add and remove a provider as it is loaded and unloaded, without disturbing a negotiation already in progress. Deploying as a plugin is therefore the supported path for this extension point.

What happens if my code throws an unexpected exception?

It depends on where. An exception from onAuthenticateReceived(...) that is a SaslFailureException rejects the authentication attempt outright, as intended; any other exception there is logged and ignored. An exception from getStreamFeatureElements(...) or getOfferedTasks(...) is logged and that provider is skipped for the round (see the note on fail-open behaviour in Deciding when to offer a task). An exception from createTask(...), or a SaslFailureException from a task's own begin(...) or onTaskData(...), aborts the whole SASL2 negotiation with <failure/>.

How do I test a task provider without a real XMPP client?

The unit tests that were added alongside this API (for example those covering the negotiation's state machine and the default provider/task behaviour) construct the relevant objects directly with mocked sessions, rather than driving a real connection. That is a reasonable starting point for testing a task's own logic in isolation. Exercising the full wire protocol against your provider is best done with an actual XMPP client library that has been updated to support SASL2 tasks, or with a raw XML test harness.

My task needs to call an external service (an SMS gateway, a push notification API, ...). Can I do that from begin(...) or onTaskData(...)?

Not synchronously, and not from those calls directly - they run on the connection's inbound processing thread and must not block on network I/O to a third party. There is currently no supported way to resolve a task step asynchronously. If your task depends on an external service, trigger the call beforehand or fire it off in the background and treat the client interaction purely as a "did this complete" check, or issue and validate the challenge, entirely from state your own code manages.
