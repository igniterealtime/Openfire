# ADR-008: Extra Domains After Resuming a Server Connection

## Status

Accepted

## Context

OF-2425 adds Stream Management (XEP-0198), including resumption, to server-to-server connections, in both directions: Openfire answers resume requests on incoming connections, and resumes the streams of connections that it opened itself when they break.

With Server Dialback, one connection can carry stanzas for several domains of the same servers (XEP-0220 § 2.6, "Multiplexing"): after the domain for which the connection was opened, the server that opened it authenticates further domains on it, each with a dialback request of its own. On an incoming connection, Openfire records each such domain as a validated domain of the session. On an outgoing connection, Openfire records each authenticated domain pair (local domain, remote domain) on the session, and the session is the route for each of them.

When a stream is resumed on a new connection, only one domain is authenticated on that new connection: the one with which the remote server authenticates it (incoming), or the domain pair for which Openfire created the session (outgoing). XEP-0198 does not say what happens to the other domains of the session.

Two facts complicate authenticating them again:

- A dialback key is generated with the stream ID that the Receiving Server sent in the stream header of the stream on which the key is sent (XEP-0185, "the Stream ID generated by the Receiving Server"). After resumption, that is the stream ID of the new connection, which differs from the stream ID by which the resumed session is known.
- XEP-0220 § 2.1.1 lets a Receiving Server close the stream when it refuses a domain. A stanza for a domain that the Receiving Server does not accept typically has the same effect.

**This decision depends on ADR-007.** Keeping the domains of a resumed incoming session is only safe because ADR-007 makes sure that the new connection belongs to the same remote server, authenticated at least as strongly as before. If ADR-007 is relaxed, this decision must be revisited.

## Options Considered

### Option 1: Refuse Resumption When a Session Has Extra Domains

**Description**: Offer or accept resumption only for sessions with a single domain.

**Consequences**:

- ✅ Nothing to authenticate again, and nothing to hold
- ❌ Remote servers that host several domains, the main use of multiplexing, never benefit from resumption

### Option 2: Incoming: Keep Only the Main Domain

**Description**: After resumption, keep only the domain that the remote server authenticated on the new connection.

**Consequences**:

- ✅ Every domain on the session was authenticated on its current connection
- ❌ The remote server does not know that the other domains were dropped. Its next stanza from one of them is refused with an error that closes the connection

### Option 3: Incoming: Keep All Validated Domains (CHOSEN)

**Description**: All domains validated on the kept session remain valid after resumption. If the remote server authenticates one of them again, Openfire accepts that.

**Consequences**:

- ✅ The remote server can continue with all its domains, as if the connection had not broken
- ✅ A remote server that authenticates its domains again after resuming is not refused
- ❌ Relies on ADR-007 to make sure that the new connection belongs to the remote server that authenticated those domains
- ❌ Dialback on the resumed connection has to use the stream ID of that connection, not that of the resumed session

### Option 4: Outgoing: Assume the Remote Server Keeps All Domains

**Description**: After resumption, send stanzas for all domain pairs of the session on the new connection, as before the break.

**Consequences**:

- ✅ No extra round trips, no stanzas held
- ❌ Openfire cannot know whether the remote server keeps extra domains after resumption. If it does not, the first stanza for such a domain closes the resumed connection
- ❌ The stanzas that were unacknowledged at the first break then go through ADR-009 a second time, and their one retry is spent on a connection that was going to fail

### Option 5: Outgoing: Authenticate Each Extra Domain Pair Again Before Sending Its Stanzas (CHOSEN)

**Description**: After resumption, Openfire authenticates each extra domain pair again with dialback on the new connection, and holds the stanzas for that domain pair, including the unacknowledged ones that are to be sent again, until it is verified. A domain pair that cannot be verified, or that the remote server refuses, is given up: its unacknowledged stanzas are handled as in ADR-009, and its other stanzas are sent over a new connection.

**Consequences**:

- ✅ No stanza is sent for a domain pair that the remote server has not accepted on the new connection
- ✅ The stanzas of each domain pair keep their order
- ✅ Works whether or not the remote server kept the extra domains
- ❌ One extra dialback round trip per extra domain pair after each resumption, during which its stanzas wait
- ❌ More state to manage: held stanzas per domain pair, and verification attempts that can be overtaken by another break

## Decision

We will **accept liberally on incoming connections, and send conservatively on outgoing connections**: Option 3 for incoming connections, and Option 5 for outgoing connections.

### Incoming connections

- A resumed incoming session keeps all its validated domains and stays registered for each of them. It also keeps its own stream ID, by which it and its domains are registered, and from which its SM-ID is made.
- Dialback on the resumed connection verifies keys with the stream ID that Openfire sent in the stream header on that connection (`LocalIncomingServerSession#getConnectionStreamID()`), which is the stream ID of the session that provided the connection. A stream that is restarted on that connection, for example after compression, uses it too.
- Dialback for a domain that is validated on the session already is accepted, and reported as valid. With `xmpp.server.session.allowmultiple` set to `false`, the session that uses the connection on which a domain is authenticated is not counted as an existing connection for that domain.

### Outgoing connections

- When the remote server confirms the resumption with `<resumed/>`, the stanzas of every domain pair of the session other than the one for which it was created are held before anything is sent on the new connection (`RequestingStreamManager#holdUntilVerified`): the unacknowledged ones, which are taken out of the Stream Management numbering until they are sent, the ones that were queued while the connection was broken, and those that are delivered for that domain pair later. They are held in order, and do not count towards the maximum number of queued stanzas.
- For each such domain pair, Openfire sends a dialback key that is generated with the stream ID of the stream header on the new connection (`LocalOutgoingServerSession#getConnectionStreamID()`). The answer of the remote server is passed to the session (`LocalOutgoingServerSession#processDialbackResult`), rather than being taken for the dialback result of the connection itself, which closes the connection on any answer other than 'valid'.
- On 'valid', the held stanzas of the domain pair are sent, in order: the unacknowledged ones first, marked as sent again, then the others. Each is numbered as it is sent.
- On any other answer, or when the new connection was not authenticated with dialback, or dialback is disabled, the domain pair is given up (`RequestingStreamManager#giveUpUnverified`). While Openfire holds the lock with which stanzas for that domain pair are routed, the domain pair is removed from the session with its route, its unacknowledged stanzas are handled as in ADR-009, and its other held stanzas are routed again after them. A stanza for the domain pair that is routed meanwhile waits for that lock, and follows them to a new connection. The session is not used again for a domain pair that it gave up.
- When the remote server does not answer within the socket timeout for server connections (`RemoteServerManager#getSocketTimeout()`), or the connection closes first, the domain pair is given up only while the session still uses that connection, the connection is open and no stanzas are queued. Otherwise its stanzas stay held, to be verified again when the stream is resumed next, or handled with the other stanzas when the session ends. Only the most recent verification attempt for a domain pair can release or give up its stanzas.
- Openfire keeps sending the stanzas of the main domain pair after an extra domain pair is refused. If the remote server then closes the stream, that is handled as any other close: the session is detached again when its stream can still be resumed, and ends otherwise, for example after a stream error from the remote server.
- While a session is detached, a domain pair that it does not have gets a connection of its own, rather than being added to the detached session. The extra domain pairs that are verified again are therefore those that were authenticated on the session before its connection broke.

## Rationale

On incoming connections, the extra domains were authenticated for the same remote server that resumes, which ADR-007 checks, so there is nothing to gain from dropping them, and dropping them would break the remote server's next stanza from one of them. Accepting a repeated dialback costs nothing, and serves a remote server that cannot know whether Openfire kept its domains.

On outgoing connections, Openfire is in the position of that remote server: it cannot know whether the other end kept the extra domains. Sending a stanza for a domain that the remote server no longer accepts would typically close the resumed connection, and spend the one retry that ADR-009 allows on a connection that was going to fail. An extra dialback round trip per extra domain pair is a small price for not risking that.

Giving up a domain pair moves its stanzas to a new connection of their own, on which that domain pair is authenticated from the start. If that fails as well, the code that opens outgoing connections returns the stanzas to their senders as for any connection that cannot be set up (with `<remote-server-not-found/>`).

### Deviation from XEP-0220 § 2.1.1

XEP-0220 (version 1.1.1), § 2.1.1, describes what the Initiating Server does when the Receiving Server answers a dialback request with 'invalid' or 'error'. Openfire deviates from it for both, when it verifies an extra domain pair again after a resumption.

For 'invalid', it says:

> In this case, the Initiating Server MUST NOT attempt to send any outbound stanzas it has queued up for routing to the Receiving Server for the domain pair but instead MUST return such stanzas to the respective senders at the Sender Domain with an &lt;internal-server-error/&gt; stanza error. Since the Receiving Server will most likely close the stream and the underlying TCP connection if that occurs (see Section 2.2.1), the Initiating Server SHOULD NOT attempt to send further stanzas for other domain pairs that have already been authorized.

Openfire does not send the held stanzas of a refused domain pair to the Receiving Server on that connection. It differs from this text in two ways:

- It routes them again, so that they are sent over a new connection after the domain pair is authenticated there, instead of returning them with `<internal-server-error/>`. Unacknowledged stanzas among them are sent again or returned as ADR-009 describes, with `<service-unavailable/>`.
- It keeps sending the stanzas of the main domain pair. If the Receiving Server closes the stream, the session is detached or ended as after any other close.

For 'error', it says:

> If the value of the 'type' attribute is "error", this indicates a problem which is not related to the validity of the dialback key provided. The error conditions are explained in detail under Dialback with Error Handling. Such an error is non-fatal for the XML stream, but the Initiating Server MUST return any queued stanzas to the respective senders at the Sender Domain with a &lt;remote-server-timeout/&gt; stanza error.

Openfire handles an answer of type 'error' as one of type 'invalid': it gives up the domain pair, and routes its held stanzas again, so that they are sent over a new connection after the domain pair is authenticated there, instead of returning them with `<remote-server-timeout/>`. Unacknowledged stanzas among them are sent again or returned as ADR-009 describes. This follows decision 2 of the OF-2425 plan, which gives up a domain pair on any answer other than 'valid', and sends its stanzas over a new connection; when that connection cannot be set up either, their senders receive an error then (see Rationale).

## Consequences

### What Becomes Easier

- Remote servers that host several domains benefit from resumption on incoming connections without any extra steps
- On outgoing connections, a remote server that dropped the extra domains on resumption costs a dialback round trip per domain pair, not a broken connection
- Dialback keys on a resumed connection, in either direction, are generated and verified with the stream ID of that connection, as XEP-0185 requires

### What Becomes Harder

- The stanzas of extra domain pairs wait for a dialback round trip after each outgoing resumption
- `RequestingStreamManager` keeps held stanzas per domain pair next to the unacknowledged and queued ones, and `onClose` handles all three
- A remote server that refuses an extra domain pair and then closes the stream, as XEP-0220 § 2.2.1 has it do, breaks the resumed connection anyway, after which the session is resumed again or ended

### Constraints

- This decision relies on ADR-007, and must be revisited if ADR-007 is relaxed
- At the time of this decision, the outgoing sessions that Openfire creates for its current connections cannot authenticate an extra domain pair with dialback, as `LocalOutgoingServerSession#authenticateSubdomain` needs a socket reader that only sessions created by `ServerDialback#createOutgoingSession` have, and those cannot be resumed. In practice, an outgoing session that can be resumed therefore has only the domain pair for which it was created, until that is changed
