Login Limits Guide

« Back to documentation index

Introduction

Openfire can limit how many times a password may be tried for user accounts, to protect them against password guessing. When too many attempts that do not succeed come from one IP address, or are made for one account, further attempts are refused for a while, and an account that is guessed at from many IP addresses is locked.

The login limits are on by default, with only the limit per username from one IP address active: it refuses that username only from the IP address that reached the limit, so where each client has its own IP address it affects no one else. Where clients share an IP address, read Things to consider first. The limits per IP address and per username from any IP address are off (0) by default, as they can affect users who did nothing wrong (see Things to consider); turn them on where they suit your network. Change the limits, or turn them all off with the On/Off switch, on the Login Limits page (Server > Server Settings > Login Limits), or through the system properties below (Server > Server Manager > System Properties). While the limits are off, nothing is counted or blocked, but a locked account is still refused: a lock stays until it ends or an administrator lifts it.

The admin console has its own, separate limits on its logins; this guide does not cover them.

How the limits work

Every password attempt is counted in three ways, each over a window of time that starts with the first attempt counted for it. A successful login gives its attempt back, so only attempts that do not succeed add up. An attempt the client abandons part-way also counts.

A limit of N allows N attempts in a window; the next is refused. A block on one username from one IP address, or on one IP address, lasts its block duration from the attempt that reached the limit, however early or late in the window that was; counting then starts again from zero. IPv6 addresses are counted by /64 network, as one network or device is usually given a whole /64. Only the third limit locks an account, as a lock applies from every IP address: if the lower, per-IP-address limits locked accounts, anyone could lock any user out by guessing on purpose.

A refused attempt's password is not checked, so the answer does not depend on it and a client cannot tell whether a guess would have been right. An attempt refused by a block from one IP address, or of an IP address, gets the same answer as a wrong password. An attempt for a locked account, or for a username blocked from all IP addresses, is told that the account is disabled, so that its user knows why they cannot log in; anyone who knows a username can therefore see whether it is locked. A locked account is refused in this way whether or not the login limits are on. Refused attempts are not counted, so a block does not extend itself.

Clients should log in with the bare username (alice). Openfire looks SCRAM credentials up under the username as the client sends it, so a SCRAM login as alice@example.org fails whatever the password; such attempts are not counted, so they cannot block or lock the account.

Attempts for usernames that have no account are counted in the same way, so the answers do not reveal which accounts exist. In a cluster, every node shares the same counts.

Which logins are counted

  • XMPP logins with a password (the PLAIN, SCRAM and DIGEST-MD5 mechanisms), over every type of connection, including BOSH and WebSocket.
  • JMX logins. Openfire is not told the IP address of a JMX client, so these count towards the per-username limit only, which is off by default.

Not counted: certificate logins (EXTERNAL), anonymous logins, and FAST tokens. A FAST token login is still refused while its account is locked, its username is blocked from all IP addresses, its IP address is blocked, or its username is blocked from its IP address. A certificate login is refused only while the account is locked: the blocks per IP address and per username do not apply to it. An anonymous login has no username, so neither applies. Admin console logins are covered by the admin console's own limits.

Settings

All settings take effect at once, without a restart. Setting a limit to 0 turns that limit off. Each window, block duration and the lock duration can be at most 1 day. A change to the block duration of the first two limits applies to blocks already in force; a change to the lock duration applies to locks set after it, as each lock keeps the end it was set with. Turning the login limits off lifts their blocks at once (an account lock stays until it ends or is lifted), but turning them on again before a block would have ended brings that block back.

Seeing and lifting blocks

Each time a limit is reached, an entry is written to the security audit log (Server > Server Manager > Security Audit Viewer). An entry for the per-IP-address limit is filed under the IP address.

An account locked by the per-username limit shows as locked on the user's Lock Out page (Users/Groups > User Summary, then the user), which says that the login limits set the lock, and where it can be unlocked. Unlocking it also resets its count. Where an account cannot be locked (the user does not exist, or the lockout provider is read-only or cannot set a lock that ends), the username is refused for the same time instead; if the account already has a lock, for example one set by an administrator, that lock is left as it is. An administrator's account is never locked by this limit: its username is refused for the same time instead, for XMPP and JMX logins, so that the administrator can still sign in to the admin console. Such a block is listed on the Login Limits page and can be cleared there, and the user's Lock Out page says that the account is not locked but that the login limits refuse it, and until when.

The blocks that are in force are listed on the Login Limits page (Server > Server Settings > Login Limits), where each can be cleared and the settings changed. Below the settings, the blocks are listed in three boxes, each titled with how many blocks it holds: usernames blocked from one IP address (the username, the IP address, the failed attempts and when the block ends), IP addresses blocked for all usernames (the IP address, the failed attempts and when it ends), and usernames blocked from all IP addresses (the username, the failed attempts, when it ends, and whether the account is also locked, with a link to its lockout page). Each box lists at most 100 blocks, those that end latest. Clearing a username blocked from all IP addresses does not unlock its account; use the Lock Out page for that.

Things to consider

  • Shared IP addresses. Many users can share one IP address, for example behind a NAT gateway or a company proxy. They share the per-IP-address count, so one person's failed attempts can block the others. Raise the per-IP-address limit, or set it to 0, where users share IP addresses. They also share each username's count from that IP address: 10 failed attempts for a username, from anyone behind the shared IP address, refuse that username to everyone behind it for the block duration (15 minutes by default), and this limit is on by default. IPv6 addresses are counted by their /64 network, as a network or household is usually given a whole /64, so every device on one IPv6 network shares a count.
  • Reverse proxies. When clients connect through a reverse proxy or load balancer, Openfire sees the proxy's IP address for every client. The per-IP-address limit then counts every user together, and the per-username-from-one-IP-address limit, which is on by default, counts each username from every client together: anyone who can reach Openfire through the proxy can keep a user out by failing 10 times for their username every 15 minutes. In that set-up, raise or turn off the per-IP-address limit, and turn off the per-username-from-one-IP-address limit (set it to 0) unless Openfire sees each client's own IP address. For BOSH, Openfire can take each client's IP address from the proxy's forwarding headers instead (httpbind.forwarded.enabled); when it does, set httpbind.forwarded.trusted.proxies to the proxy's IP addresses, as otherwise any client can send those headers itself and choose the IP address that the limits count. WebSocket connections are always counted under the IP address that connects to Openfire, which behind a proxy is the proxy's.
  • Deliberate lock-outs. Anyone who knows a username can lock that account by guessing at it until the per-username limit is reached. The lock ends after the lock duration. This limit is off by default; when turning it on, set it well above the number of attempts a genuine user makes, or leave it at 0 and rely on the per-IP-address limits. An administrator's account is not locked: its username is refused for the lock duration instead, for XMPP and JMX logins, so that a deliberate lock-out cannot keep an administrator out of the admin console.
  • Saved passwords. A client with an outdated saved password keeps trying it, and may block its own IP address or lock its account. The security audit log shows where this happens.
